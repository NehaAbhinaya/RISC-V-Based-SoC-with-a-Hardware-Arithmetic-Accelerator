INTRODUCTION
Problem Statement
Arithmetic-intensive applications repeatedly perform multiplication, division and multiplyaccumulate operations. Executed entirely in software on a general-purpose processor, these
increase workload and execution time. This project designs a compact RISC-V based SoC in
which the processor only configures and dispatches jobs, while a dedicated Arithmetic
Accelerator (ADD, SUB, MUL, DIV, MAC) and a DMA Controller perform the data
movement and computation off the processor's critical path.

Proposed System Aims
Stage operand blocks in Data Memory from software.
Move operands to the accelerator and results back to Data Memory with a DMA
Controller, without the processor copying data word by word.
Execute ADD, SUB, MUL, DIV and MAC on a pipelined hardware datapath.
Keep the RISC-V core limited to configuration, job dispatch and result handling.
Report job status, results and errors over UART and drive status lines on GPIO.
Let an external host configure the accelerator and read results over SPI, independent
of the processor's instruction stream.

PROPOSED SoC ARCHITECTURE
The VeeR EL2 RISC-V core is the central controller. Its two external bus interfaces
(instruction fetch and load/store) are converted to AXI4-Lite and connected, together with
the DMA Controller (and optionally an SPI bridge, see Decision D2), to one AXI4-Lite
interconnect that routes every access to the memories and peripheral register banks by
address.
The compute path is Data Memory → DMA Controller → Arithmetic Accelerator → DMA
Controller → Data Memory. The DMA reads operand pairs from Data Memory over the
fabric, streams them into the accelerator over a dedicated valid/ready link, receives results
over the same link, and writes them back to Data Memory over the fabric. The processor is
involved only before the job (configuration) and after it (result read-out, UART logging,
GPIO update).
Components
VeeR EL2 RISC-V Processor — central controller (provided).
AHB-Lite → AXI4-Lite bridges (×2) — one for instruction fetch (read-only), one for
load/store; also convert 64-bit core data width to the 32-bit fabric width.
AXI4-Lite Interconnect — S masters × 8 slaves; address decode, arbitration,
permissions, DECERR.
Instruction Memory — AXI4-Lite slave, read-only through the fabric (loaded by
testbench $readmemh ).
Data Memory — AXI4-Lite slave; operand and result buffers.
Arithmetic Accelerator — AXI4-Lite register slave + dedicated streaming link to the
DMA.
DMA Controller — AXI4-Lite register slave and AXI4-Lite master; dedicated
streaming link to the accelerator.
SPI Controller — AXI4-Lite register slave (CPU-driven SPI master); external-access
path per Decision D2.
UART, Timer, GPIO — AXI4-Lite register slaves.

Interrupt Controller (VeeR PIC) — aggregates six interrupt lines into the core.
Selected IPs
1. Arithmetic Accelerator — memory-mapped datapath: ADD, SUB, MUL, DIV, MAC,
pipelined.
2. DMA Controller — autonomous operand/result mover and bus master.
3. SPI Controller — memory-mapped SPI peripheral exposing accelerator access to an
external host.
Process Flow
Software stages operand pairs in Data Memory
→ RISC-V (LSU → fabric) configures Accelerator, then DMA, then sets DMA
start
→ DMA (fabric master) reads operand pair A,B from Data Memory
→ DMA streams the pair into the Accelerator (dedicated link)
→ Accelerator computes (pipelined) and streams result back to the DMA
→ DMA (fabric master) writes the result word to Data Memory
→ after the last result: Accelerator/DMA raise interrupt → PIC → RISC-V
→ RISC-V reads status/results, logs over UART, updates GPIO
→ (independently) an external host issues jobs / reads results over SPI

Design Decision D1 (resolved): the DMA is a genuine AXI4-Lite master ( s02 ). The earlier
dedicated DMA-to-Data-Memory port is no longer needed; Data Memory has a single
AXI4-Lite slave port. Cost: the interconnect handles one transaction at a time, so CPU and
DMA share fabric bandwidth (see Data Path §7).
Design Decision D2 (open): how an external SPI host reaches the accelerator registers.
Option A (recommended): an SPI-slave-to-AXI4-Lite-master bridge as a fourth
master s03 (permissions: read/write ACC registers, read DMEM). Requires changing

the generator preset from 3×8 to 4×8 (one table line + regenerate; the interconnect
core is already parameterised for any S_COUNT).
Option B: shadow register set inside the SPI controller that the CPU services. No extra
master, but the CPU must poll — it defeats the "independent of the processor"
requirement in the abstract.

Handshake rules every block must follow
A transfer happens on a clock edge where valid && ready . valid must not depend
on ready , must stay asserted with stable payload until accepted. ready may depend
on valid .
A slave must accept AW and W in either order and in different cycles (the fabric
forwards AW first, then W after capturing it). A slave may wait for both before
responding.
Exactly one bvalid per write and one rvalid per read, always, even for invalid
offsets (use SLVERR).
Every slave must always respond — the fabric has no bus timeout, so one stuck slave
stalls the whole SoC.

Conversion requirements
Topic

Requirement

Width 64 → 32

A 64-bit AHB transfer becomes two sequential 32-bit AXI4-Lite transfers
(low word first); hrdata[63:0] is assembled from both reads. Sub-word
and word stores map to one beat with the correct wstrb .

Address phase / data
phase

AHB pipelining (address of next transfer during data of current) is absorbed
by the bridge; hready low until the AXI4-Lite response returns.

Error mapping

bresp / rresp ≠ OKAY → hresp = 1 (two-cycle AHB error sequence).
DECERR and SLVERR both become an AHB error.

awprot / arprot

Drive 3'b000 (privileged, secure, data); instruction fetch 3'b100 .

Reset

Bridge reset = rst_n (active-low) while the fabric gets rst = ~rst_n .

CONTROL PATH
1. Purpose
The control path carries configuration, commands and status between the RISC-V core and
the accelerator, DMA, UART, Timer, GPIO and SPI. It is physically the same fabric as the
data path's memory traffic but carries only a handful of register accesses per job.

2. Control Path Architecture
Write: RISC-V store → LSU bridge → s01 AW + W → fabric (grant, decode,
permission) → mNN AW + W → register written → mNN B → s01 B → bridge → hready .
Read: RISC-V load → LSU bridge → s01 AR → fabric → mNN AR → mNN R (rdata,
rresp) → s01 R → bridge → hrdata . A register access takes several clocks (arbitration +
decode + slave response); the core stalls via hready .

3. Memory-Mapped Control
All peripherals are accessed with ordinary loads/stores at the addresses in the Memory
Map. The upper address bits select the slave in the fabric; the low 12 bits select the register
inside the slave.
4. Peripheral Register Access
Only the LSU master ( s01 ) can reach peripherals. An IFU or DMA access to a peripheral
address returns DECERR, which the bridge turns into an AHB error (core trap) — this
catches wild pointers and DMA misprogramming.
5. System Initialization and Control Sequence
Reset released (rst_n high → rst low)
→ firmware starts from IMEM 0x0000_0000
→ initialise UART (baud), Timer, GPIO, SPI, PIC
→ write operand pairs A0,B0,A1,B1,… into DMEM
→ ACC_OPCOUNT = N, ACC_CTRL.opcode = op, ACC_IRQ_EN = 1
→ DMA_SRC_ADDR, DMA_DST_ADDR, DMA_LENGTH = N, DMA_CTRL = start | irq_en
→ (CPU free to do other work or wait for interrupt)
→ irq → ISR: read DMA_STATUS / ACC_STATUS, read results from DMEM, UART
log, GPIO update

6. UART Control
RISC-V → UART_CTRL (enable, baud) → UART_TXDATA → serial out ; polled via
UART_STATUS or interrupt-driven. Used for logging only.

7. Timer Control
TIMER_COMPARE , TIMER_CTRL.enable → counter → match → irq_timer . Reading
TIMER_COUNT at job start and end gives job duration; periodic mode can auto-trigger jobs.

8. GPIO Control
GPIO_DIR , GPIO_OUT drive status/error LEDs; gpio_in edges (manual trigger) raise
irq_gpio .

9. SPI Controller Control
CPU-driven SPI master: SPI_RCLK (divider) → SPI_CR (enable, master, CPOL/CPHA) →
SPI_SSR (select) → SPI_DTR writes → wait on SPI_SR / irq_spi → SPI_DRR reads.
External host access follows Decision D2.
10. Arithmetic Accelerator Control
ACC_CTRL (opcode) + ACC_OPCOUNT → armed. The job starts when the DMA delivers the
first operand pair (or via ACC_CTRL.start in direct mode). FSM: IDLE → CONFIG → RUN →
DRAIN → DONE .

11. DMA Controller Control
DMA_SRC_ADDR , DMA_DST_ADDR , DMA_LENGTH , then DMA_CTRL.start . After that the DMA
runs on its own master port and the dedicated stream until DMA_STATUS.done or an error.

12. Accelerator / DMA Coordination
dma_op_valid/ready governs operands into the accelerator, dma_res_valid/ready
governs results back, dma_last tags the final pair so the accelerator drains and signals

completion. The DMA keeps a small result FIFO so a stalled fabric write cannot deadlock
the accelerator pipeline.
13. Status Monitoring
ACC_STATUS , DMA_STATUS (+ DMA_ERR_ADDR ), SPI_SR , UART_STATUS , TIMER_STATUS are

pollable at any time.
14. Interrupt-Based Control
event (done / error / RX / match / edge)
→ irq_xxx → PIC (mask, priority) → VeeR external interrupt
→ ISR identifies source, services it, clears the flag (W1C / read-clear),
returns

15. Complete Control Path
Configuration and status: VeeR → LSU bridge → fabric → register bank . Events return
on the interrupt wires, not on the bus.

DATA PATH
1. Purpose
The data path moves operand and result words. Memory traffic uses the same AXI4-Lite
fabric (DMA is a master); the operand/result stream between DMA and accelerator is a
dedicated link.
2. Operand Path
DMEM operand block
→ fabric (m01 read, DMA = s02) → DMA
→ dedicated stream (dma_op_*) → Arithmetic Accelerator (pipelined ALU)
→ dedicated stream (dma_res_*) → DMA result FIFO
→ fabric (m01 write, DMA = s02) → DMEM result block

3. Data Width Progression
32-bit everywhere (fabric, stream, registers). To decide before the ALU is coded: MAC
accumulation may need a wider internal accumulator (e.g. 64-bit) with the low word visible
in ACC_ACC_REG ; the high word can be a second register ( ACC_ACC_HI ) to avoid silent
overflow.
4. Streaming vs. Stored Data
Words are streamed one at a time between DMA and accelerator (valid/ready) and stored in
DMEM at both ends. The accelerator keeps no persistent operand/result storage beyond its
pipeline.
5. External Access Path via SPI
External host → spi_sclk / mosi / miso / cs_n → SPI bridge (D2 option A) →
s03 master port
→ fabric → ACC registers (m05) or DMEM (m01) → response → frame back to
host

6. Role of RISC-V in the Data Path
The core never touches data during a DMA job. It writes the operand block beforehand and
reads the result block afterwards (through the same LSU path, sharing fabric time with the
DMA).
7. Data Path and Control Path Interaction
Because the fabric serialises one transaction at a time, DMA traffic delays CPU accesses and
vice versa. Each operand pair costs 3 fabric transactions plus slave latency, so DMA
throughput is bounded by roughly 1 / (3 × transaction latency) pairs per cycle — measure
this in simulation and compare against the CPU-only software baseline to demonstrate the

speed-up. AXI4-Lite has no bursts, so there is no way to amortise address overhead; that is
the cost of choosing AXI4-Lite over full AXI4.
8. Data Path Design Requirements
Accelerator accepts a new operand pair every cycle when dma_op_ready is high (true
pipelining).
dma_last must make the accelerator drain exactly the in-flight pairs before done .
DMA result FIFO depth ≥ accelerator pipeline depth + 2 to avoid deadlock under
fabric contention.
Divide-by-zero sets ACC_STATUS.error , produces a defined result (e.g. all ones), and
must not hang the stream.
Any non-OKAY response on the DMA master port aborts the job, sets
DMA_STATUS.error and DMA_ERR_ADDR .
Operand and result blocks must lie inside DMEM and be word aligned
(misaligned/out-of-range → DECERR/SLVERR → job abort).

DESIGN REQUIREMENTS SUMMARY
1. Every AXI4-Lite slave must always respond (OKAY, SLVERR for bad offsets). No
blocking reads/writes — the shared fabric has no timeout, so one stuck slave freezes
the whole SoC.
2. All slaves must tolerate AW and W arriving in different cycles/order, honour wstrb ,
and hold rvalid / bvalid until accepted.
3. Single clock clk ; reset is active-low rst_n outside, active-high rst = ~rst_n at
the interconnect.
4. Bridges must convert 64-bit ↔ 32-bit, map non-OKAY responses to AHB errors, and
never lose the AHB pipeline address.
5. Permissions are enforced by the fabric (see matrix); firmware must not write IMEM or
reach peripherals from IFU/DMA.
6. DMA is a single-beat master; its throughput must be characterised and reported.
7. The reused UART/SPI cores need the modifications listed (IDs, clocks, interrupts,
strobes, error responses).
8. Verification: unit testbench per IP, fabric regression (already complete), system test
running real firmware on VeeR with UART output check, DMA job end-to-end, and
the SPI external-access path.
