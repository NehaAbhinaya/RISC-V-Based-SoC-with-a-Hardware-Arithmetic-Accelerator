Design and RTL Implementation of a RISC-V Based SoC with a
Hardware Arithmetic Accelerator
Detailed Project Specification
This document follows the same structure and level of detail as the reference honoursproject specification you shared (block diagram → full signal lists → memory-mapped
register access → control path → data path → design requirements), applied to your project: a
VeeR EL2 RISC-V SoC with a hardware Arithmetic Accelerator, DMA Controller, and SPI
Controller.
The reference document confirms the course's underlying bus architecture is AHB-Lite at
the processor core, bridged to APB for peripheral register access, built around the VeeR
EL2 RISC-V core. This specification adopts that same real architecture (replacing the
generic custom bus assumed in the earlier draft) so it is consistent with what your provided
core and tooling actually expect.

INTRODUCTION
Problem Statement
Arithmetic-intensive applications often require repeated multiplication, division, and
multiply-accumulate operations, which increase processor workload and execution time
when performed entirely in software. This project proposes a RISC-V based SoC with a
dedicated hardware Arithmetic Accelerator, where the VeeR EL2 processor handles
system-level configuration and result reporting, while the repetitive, high-throughput
arithmetic work is offloaded to dedicated RTL hardware, off the processor's critical path.
Proposed System Aims
Accept operand data staged in Data Memory by software.
Autonomously move operand blocks into the accelerator and results back, using a
DMA Controller, without occupying the processor one word at a time.
Execute ADD, SUB, MUL, DIV, and MAC operations on a pipelined hardware datapath.
Reduce processor workload by keeping the RISC-V core limited to configuration, job
dispatch, and result handling.
Report job status, results, and error flags to an external host over UART.
Expose accelerator configuration and results to an external host/test bench over SPI,
independent of the processor's own instruction stream.

PROPOSED SoC ARCHITECTURE
The VeeR EL2 RISC-V processor acts as the central controller and communicates with
memories and peripherals through an AHB-Lite interconnect, bridged to APB for all
memory-mapped peripheral register access. The architecture follows a hardware-software

co-design approach: the processor performs configuration, job dispatch, and result
interpretation, while the high-volume operand movement and the arithmetic computation
itself run entirely in dedicated hardware.
The compute path consists of Data Memory → DMA Controller → Arithmetic Accelerator
→ DMA Controller → Data Memory. The DMA Controller autonomously streams operand
blocks from Data Memory into the accelerator's pipelined datapath and streams computed
results back once the accelerator asserts completion. The processor is only involved before
the job starts (configuration) and after it ends (result read-out, logging, status update) —
never during the transfer or computation itself.
The SoC consists of the following components:
VeeR EL2 RISC-V Processor — central controller; configures and controls the
Accelerator, DMA Controller, and other peripherals; dispatches jobs; interprets results.
Instruction Memory — stores the firmware that configures and controls the system.
Data Memory — stores operand blocks (staged by software) and result blocks
(written by the DMA Controller); accessible to the processor over AHB-Lite and to the
DMA Controller over a dedicated data port (see §Data Path Architecture — Design
Decision D1).
AHB-Lite Interconnect — connects the processor core to Instruction Memory, Data
Memory, and the AHB-to-APB bridge.
AHB-to-APB Bridge / APB Decoder — converts AHB-Lite register accesses into APB
transactions for all peripheral register banks.
Arithmetic Accelerator — the primary custom IP; performs ADD, SUB, MUL, DIV,
and MAC on a pipelined datapath.
DMA Controller — autonomously transfers operand blocks into the Accelerator and
result blocks back to Data Memory.
SPI Controller — exposes Accelerator configuration/result registers to an external
host, independent of the processor's own bus transactions.
UART — transmits job status, results, and error flags to an external host.
Timer — timestamps job start/completion; can trigger periodic accelerator jobs.
GPIO — drives status/error indicator lines and captures manual trigger/reset input.
Interrupt Controller (VeeR PIC) — aggregates interrupts from Accelerator, DMA, SPI,
UART, Timer, and GPIO to the processor core.
Selected IPs
1. Arithmetic Accelerator — memory-mapped datapath implementing ADD, SUB,
MUL, DIV, MAC with a pipelined multiply/MAC stage; the primary custom IP.
2. DMA Controller — memory-mapped engine that autonomously transfers operand
blocks from Data Memory into the Accelerator and streams results back, so the
processor is not occupied moving data one word at a time.

3. SPI Controller — memory-mapped peripheral (SCLK generation, MOSI/MISO shift
register, chip-select control) exposing Accelerator configuration/result registers for
external access.

Design Decision D1 (flagged, same as the reference project's treatment of FFT→Data
Memory): the DMA Controller's high-volume operand/result transfer should not be forced
onto the shared AHB-Lite bus as a second bus master, since that adds arbitration
complexity the course template avoids elsewhere. Instead, Data Memory exposes a second,
dedicated data port used only by the DMA Controller for burst operand reads and result
writes, while the processor continues to access Data Memory normally over AHB-Lite for
anything software needs to touch directly. This mirrors exactly how the reference project
deferred and separated its FFT-to-Data-Memory connection from the LSU AHB-Lite table.
Confirm this decision before RTL begins — the alternative is a true second AHB-Lite
master with round-robin arbitration, which is more faithful to a "real" SoC bus but adds
verification surface area for comparatively little benefit at this project's scope.

Per the abstract, SPI exposes accelerator configuration/result registers to an external host.
Implementation choice to confirm: a simple register bridge (SPI frame = {addr, r/w, data}

which the SPI Controller relays as its own APB access), vs. a shadow register set the CPU
also polls — the bridge approach needs the SPI Controller to become an APB master, adding
a second APB master to arbitrate; the shadow-register approach avoids that at the cost of
the CPU having to periodically service external SPI requests.

CONTROL PATH
1. Purpose
The control path defines how the VeeR EL2 processor configures, starts, monitors, and
controls the Accelerator, DMA Controller, and other peripherals, and how status,
completion, and error information is returned to it. The control path is separate from the
compute data path: the control path carries configuration, commands, and status; the
compute data path carries the actual operand and result words.

6. UART Control
Configuration: UART_CTRL (enable, baud), interrupt enable if used. Control flow: RISC-V →
UART_CTRL/UART_TXDATA → UART configured/transmitting → UART ↔ Host PC . The
processor polls or is interrupted by UART_STATUS to know when TX/RX is ready. UART is
used for external reporting, not for the computation itself.
7. Timer Control
RISC-V → TIMER_COMPARE, TIMER_CTRL (enable) → Timer counts → compare/timeout
event → irq_timer → PIC → RISC-V . Can be used to timestamp job duration or auto-

trigger periodic accelerator jobs.
8. GPIO Control

RISC-V → GPIO_DIR → GPIO_OUT → external pins driven . On the input side: external
event → gpio_irq (if enabled) → PIC → RISC-V . GPIO is a general status/control

interface, not part of the compute data path.

10. Arithmetic Accelerator Control
RISC-V → ACC_CTRL (opcode, opcount) → ACC_CTRL.start → Accelerator FSM: IDLE →
CONFIG → RUN → DRAIN → DONE → irq_acc → RISC-V reads ACC_STATUS/ACC_RESULT .

11. DMA Controller Control
RISC-V → DMA_SRC_ADDR/DMA_DST_ADDR/DMA_LENGTH → DMA_CTRL.start → DMA reads
operand block from Data Memory (dedicated port) → streams to Accelerator →
streams results back → writes result block to Data Memory → irq_dma → RISC-V
reads DMA_STATUS .

12. Accelerator/DMA Coordination
The Accelerator and DMA Controller coordinate directly through the dedicated streaming
interface (§7B/§8C) without processor involvement during the transfer —
dma_op_valid/ready governs operand flow into the Accelerator, dma_res_valid/ready
governs result flow back out, and dma_last tells the Accelerator when the job's final
operand pair has arrived. The processor's role is limited to arming both blocks beforehand
and reading status afterward.
13. Status Monitoring
The processor can poll ACC_STATUS , DMA_STATUS , SPI_STATUS , and UART_STATUS at any
time, or rely on interrupts (§14) for event-driven operation.

15. Complete Control Path
Configuration, dispatch, and result-handling all travel: RISC-V ↔ AHB-Lite ↔ AHB-to-APB
Bridge ↔ APB ↔ Peripheral register bank , while interrupts travel the reverse direction
through the PIC. This is entirely separate from the compute data path described below.

DATA PATH
1. Purpose
The compute data path carries the actual operand and result words through the system,
separately from the control path's configuration/status traffic.
2. Operand Path



Data Memory (operand block, port B) → DMA Controller → Arithmetic Accelerator
(pipelined ALU) → DMA Controller → Data Memory (result block, port B)

Software's only involvement is writing the operand block into Data Memory before the job
starts and reading the result block (or the direct ACC_RESULT register, for single-op tests)
after the job completes.
3. Data Width Progression
Operand and result words are 32-bit throughout the datapath ( dma_op_data_a/b ,
dma_res_data , and the direct ACC_OPERAND_A/B / ACC_RESULT registers are all 32-bit).
Design requirement to confirm: MAC accumulation may require wider internal precision
(e.g., a 64-bit internal accumulator with 32-bit read-back through ACC_ACC_REG ) to avoid
overflow across a long operand sequence — this should be finalized before the ALU
datapath is coded.
4. Streaming vs. Stored Data
Operand and result data is streamed between the DMA Controller and the Accelerator
(valid/ready handshake, one word at a time, pipelined), but is stored in Data Memory at
both ends of the transfer. The Accelerator itself holds no persistent operand/result state
beyond what the pipeline needs to keep in flight.
5. External Access Path via SPI



External Host → spi_sclk/mosi/miso/cs_n → SPI Controller → [bridge or shadow
registers] →
Arithmetic Accelerator / DMA registers

This path lets an external host issue a job and retrieve its result without touching the
processor's own instruction stream, satisfying the abstract's "External access" requirement.
6. Role of RISC-V in the Data Path
The processor never touches operand or result data directly during a DMA-driven job — it
only writes/reads the block boundaries in Data Memory before/after, and
configures/monitors through the control path. This is what frees the processor from the
high-volume data movement.

7. Data Path and Control Path Interaction
The two paths share the same physical Data Memory and the same APB register interface
for configuration, but carry logically distinct traffic: control-path traffic is words-per-job (a
handful of register writes), while data-path traffic is words-per-operand (potentially many
per job). Keeping the DMA's operand/result movement off the shared AHB-Lite bus (Design
Decision D1) is what keeps these two paths from contending for bandwidth.
8. Data Path Design Requirements
The DMA's dedicated Data Memory port and the Accelerator's dedicated streaming
interface must be finalized before RTL — both are currently specification-level
definitions, not verified interfaces.
The Accelerator's pipeline must accept a new operand pair the cycle after the previous
one issues, while earlier results are still draining (true streaming, not stall-peroperand).
dma_last must be sampled correctly so the Accelerator's DRAIN state flushes
exactly the right number of pipeline stages before asserting irq_acc .
Divide-by-zero and any other error conditions must set ACC_STATUS.error and must
not hang the pipeline — a following DMA transfer should be able to proceed after an
errored job.
MAC accumulator width/overflow behavior (see §3 above) must be decided and
documented before the datapath is coded.

OPEN ITEMS REQUIRING CONFIRMATION

2. SPI external-access implementation (§9): register bridge (SPI Controller as a second

3. VeeR PIC interrupt-line count/encoding actually instantiated for this SoC (2–255
configurable sources; this spec assumes 6).
4. MAC accumulator internal width and overflow/saturation behavior.
